§1

Platform

Tenant lifecycle, cross-org troubleshooting, support, billing, audit.

1.1 · "Suspend" does nothing P0

Grepped every RLS policy and helper for organizations.status: zero matches. Directory.tsx:71–73's Suspend button writes the column and nothing reads it — a suspended org's staff, guardians, and players retain every permission unchanged. This is the single highest-severity finding in this audit: the one control that looks like it enforces something and doesn't.

Entitlement lifecycle is also binary today, not the roadmap's phased Trial → Active → Grace period → Restricted → Suspended (platform-implementation-roadmap.md:172-184) — the Directory's checkboxes are a light switch, not a lifecycle.

1.2 · No cross-org troubleshooting path existed for Platform Admin built 09-11

Every "view as" mechanism was club-scoped, callable only by that club's own club_it_admin: start_impersonation() took a p_club_id; effective_access_for() required a live session for that exact club triple. tournament_it_admin deliberately has its own separate, tournament-scoped audit function rather than a shared one (resolved by explicit ruling, club-entitlement-gap-analysis.md §13) — both stay exactly as they were.

Built as a third, additive tier: start_platform_impersonation(org_id, target_user_id, reason), keyed on org_id not club_id so it reaches a Tournament-only org too. effective_access_for_platform() aggregates every club and every tournament the target touches in that org into one readout. Same audit discipline (the platform admin's email lands in audit_log, never the target's — verified live), same visible banner (a new tier in ImpersonationBanner.tsx, distinguishable from the club-scoped one). New "Troubleshoot" tab in /platformconsole, driven end-to-end through the real UI: picked an org showing its held entitlements inline, viewed as a team manager, got back their real permission bundle, ended the session, watched the banner clear.

1.3 · Support queue shows no entitlement context P1

The support_requests/support_request_messages system itself is solid and genuinely org_id-generic, exactly as promised when it was built — Tournament used it with zero schema changes. But SupportQueue.tsx:48-51 never shows which product(s) the filing org holds; Platform Admin has to tab over to Directory to find out before triaging.

1.4 · Billing: a form that could never submit, and RLS wide open by design both fixed 09-11

Bug, fixed: BillingConsole.tsx's "Create invoice" form had no billingAccountId field — createPlatformInvoice required it and every submission failed. Fixed by looking the account up server-side from orgId instead (a platform account is 1:1 per org).

RLS, fixed: billing_invoices_read and siblings granted any is_org_member(org_id) full read — any coach, guardian, or player could read every invoice belonging to their org, other families' included. Narrowed via two new helpers mirroring can_review_billing_invoice's own branching (platform admin; the named payer; or staff/tournament-staff holding a finance permission at that specific club/tournament). Verified live: a plain coach dropped from reading their club's billing account to refused; the club manager (holds manage_finances) unaffected.

Left open: tournament billing's write side still authorizes on is_org_admin alone rather than the tournament permission catalog, and the tournament billing design doc's 6 proposed permission keys (§3.4) still don't reconcile with the 2 already-live ones — unchanged by this pass.

1.5 · No platform-wide audit read surface

Club and Tournament each got their own scoped audit RPC (club_audit_log(), tournament_audit_log()). Platform Admin has neither a cross-org view nor a documented direct-read path — needed once §1.2's backdoor exists, not before.

§2

Clubs

Mostly resolved by prior phases; two new findings surfaced while investigating billing.

2.1 · Already resolved — recap only

docs/club-entitlement-gap-analysis.md covers this product in full. P0 (items 1–6) and 5 of 7 P1 items are built and verified. P1-#13 (IT scoping) is explicitly resolved, not deferred. Nothing here reopens any of that.

2.2 · Two unreconciled financial systems P1

Clubs now run fee_charges/payments (pre-existing) alongside the new billing_invoices/billing_payment_submissions domain, with no bridge. Finances.tsx:74-114 renders them as two separate, unrelated lists — its own empty state admits it: "No billing-domain invoices yet. Existing fee charges remain visible above." No backfill, no shared source_type/source_id linkage, no product decision on which is authoritative. Every existing dashboard (ActionCenter, Reports) reads fee_charges only — revenue will visibly split across two places once billing goes live.

2.3 · The club-wide Finances tab never got the permission-catalog treatment P1

canManageFinances = access.isClubManager || access.role === 'staff' (page.tsx:100) is a role-literal check predating Phase 0's permission foundation — distinct from PlayerProfile.tsx's correctly-migrated per-player flag. Concrete consequence: treasurer, the role created specifically as "Finance specialist," cannot open or manage the club's own Finances tab. The new billingInvoices query rides on this same broken flag, so fixing it now also fixes who sees billing correctly.

§3

Tournaments

RBAC foundation is live; almost nothing built on top of it has a workspace yet.

3.1 · RBAC foundation live, temporarily undocumented and untested

The full tournament_staff authorization layer is live and unaffected by this pass (phase8a–phase8d confirmed applied). Its documentation and tests were deleted (§0) — restore both before building further on top.

3.2 · No organizer console anywhere in this repo P1

Grepped all 24 tournament-referencing routes: beyond the public list and the club-side team/roster pages, there is no page for an Organizer or Team Coordinator to do anything — tournament_staff_directory() and decide_tournament_entry() both exist in the database and are called by nothing in src/.

Registration itself has no UI either — grepped every action file for an INSERT into tournament_entries: none. Every entry in the live database exists because it was inserted directly. tournament_categories (divisions, fees, capacity) has the same status: real table, zero owner-side UI.

3.3 · Competition data — correctly schema-only where it belongs to the proxied engine

venues/matches/match_events/player_tournament_results belong to the frozen, proxied Tournament Manager app by explicit standing rule — their absence of UI here is by design. tournament_categories is different: it's the host org's own configuration, not the proxied engine's runtime data, and belongs with §3.2's organizer console.

3.4 · Tournament billing proposes a second, unreconciled permission vocabulary P0

tournament-billing-integration.md:178-187 proposes six new permission keys (manage_entry_invoices, verify_tournament_payment, etc.) — none exist in the live catalog. The catalog already has manage_tournament_finances/view_tournament_finances, already granted to organizer and treasurer. The new document neither reuses nor references them.

This is precisely the risk the platform roadmap warns against in its own words: "Tournament work can accidentally create a second permission model" (platform-implementation-roadmap.md:963). Reconcile before building any tournament finance screen.

3.5 · Officiating — confirmed unchanged, schema and RLS only

No UI in this repo, consistent with §3.1's own scope statement. No new findings; restoring the deleted test is the only action item.

§4

Cross-cutting risks

  • The same "role string reused across two tables" pattern that caused the has_tournament_permission scope-leak bug now exists in miniature in billing_invoices.payer_type — one flat CHECK spanning club and tournament payer types with no context-aware gating yet.
  • Club's and Tournament's RBAC were each proven with a real RLS suite before being trusted. The billing series has one unit-test file for invoice math and no RLS test at all — nothing proves the broad read policy in §1.4 is deliberately temporary rather than quietly permanent.
  • organizations.status (§1.1) and billing_accounts.status are two independent, currently-inert suspend switches. Wiring them up separately later risks an org that's billing-suspended-but-access-active, or the reverse, silently.
