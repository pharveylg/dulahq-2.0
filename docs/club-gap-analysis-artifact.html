01 Organization member profiles

What exists. club_staff is (club_id, user_id, role, created_at, updated_at, created_by, org_id) — no profile fields at all. users is (id, name, email, role, linked_referee_id, created_at). That is the entire staff-facing data model: a name, an email, a role string. Contrast players, which has photo_url, notes, dob, preferred_foot, development_status, and a full six-tab canonical profile. There is no equivalent for a coach, team manager, treasurer, secretary, or club manager — not a stub, nothing.

Orphaned second staff table

A second staff table, team_staff — (id, team_id, name, role, role_other, phone, org_id) — has no user_id at all, so it can't participate in RLS, permissions, or assignment. It has zero rows and zero code references outside generated types. It predates club_staff + user_assigned_teams and was never retired.

Committee Heads cannot exist as a role at all — the club_staff.role CHECK permits exactly eight roles, none of them committee-shaped, and there is no committees table anywhere.

P1 — missingteam_staff — removeCommittees — defer

The account / membership / profile split: account (users: name, email, auth) is already correct. Org membership (club_staff + user_assigned_teams) covers role, team assignment, and primary-coach designation — but not status (§4) or a considered join date. A role-specific profile — photo, phone, bio, certifications with expiry — is genuinely new; nothing today is even a weak substitute.

02 Club identity and branding

clubs.branding jsonb, clubs.settings jsonb, clubs.about text, and clubs.location text exist. In the live data, branding/settings are {} on every club, while about/location hold real prose — written directly by the seed script, not through any UI. The only club-editing surface in the app is a rename form. There is no club logo field, and no team logo/badge column at all.

Branding precedence is undefined

organizations carries its own logo_url/accent, used today only by the platform-admin org list. The showcase data already has two orgs each owning two clubs — "the org has a logo, the club has none, which one prints on a roster export" is the live shape today, not a hypothetical. RosterBuilder.tsx's TXT export already prints an unbranded header.

P0 — missing UIP1 — precedence rule, resolve before Tournament

03 Organization structure / org chart

Nothing visual exists. The relationships are real and queryable — team assignment, primary-coach designation, functional role, effective permission — but nothing renders them as a structure. The Staff tab is a flat list with inline team chips; it does not show a team's chain or the club-wide functional roles as one picture.

The underlying data is now complete enough (post primary-coach work) that a chart is a read-only rendering problem, not a modeling problem — the same "derived, never a second dataset" pattern already used for roster state. Explicitly exclude players/guardians: this is a staff org chart, and folding families in would conflate "who runs this club" with "who is enrolled in it."

P2 — missing, low risk

04 Organization membership lifecycle

Three separate, incompatible lifecycles exist today — which is itself the finding:

Person typeLifecycle today
Guardianaccount_status: active / no_account, plus invited_at. A real, if minimal, state machine.
Playermemberships.status exists — table has zero rows. No code path has actually exercised it, so its real vocabulary is unverified.
StaffNothing. No status column. No invitation flow — a person must already hold an account. "Remove" is a hard DELETE from club_staff, which cascades away their assignment history too.
P0 — staff has no lifecycle, hard-deletes on removal

Per the request's own instruction not to build a separate flow per role, the shared shape should be invited → active → suspended → archived, with archived — never deletion — as the terminal state for anyone who held real data.

05 Communication and contactability

Announcements.tsx supports real audience targeting (club, team, players, guardians, coaches, staff). Guardians have a working notification path gated on a real per-relationship permission. Staff have none — nothing currently writes a staff-targeted notification row.

Three permissions gate nothing

communicate_with_club, manage_availability, and manage_forms are granted to every guardian by default and surfaced in the club admin's per-guardian permission grid — but none of the three strings appears anywhere in application code beyond the permission catalog itself. A club admin can "revoke" a capability that was never real in either direction. This is a currently false claim in the permission system, not a missing feature.

Separately, announcement_reads exists as a table and is referenced nowhere in application code — schema with no feature.

P0 — dead permissions, fix nowP1 — staff notification resolverP2 — wire announcement_reads

06 Organization directory

The platform's only "directory" lists organizations, for the platform admin — not people, and not club-scoped. There is no club-wide staff, player, or guardian directory.

Confirmed live, not theoretical

Verifying the primary-coach UI as the club manager, every staff member except the signed-in viewer rendered as "Unknown" with a blank email. The joined users(name, email) query is emptied by public.users's own self-row-only SELECT policy for everyone but the caller. The club manager — who owns this data — could not read their own staff's names.

P0 — confirmed regressionP2 — club-wide directory once fixed

Fix path: a narrow club_staff_directory() RPC mirroring the IT role's already-established it_club_directory() pattern — not a broad widening of public.users' policy.

07 Documents, qualifications, organizational records

document_uploads is a mature, working feature for player-scoped documents — categories, role-gated writes, guardian/player read-only visibility. This should not be duplicated. It is, however, entirely player-centric: nowhere for coach certifications, club policy documents, or any staff-facing document.

P2 — staff qualificationsDefer — club policy docs

The clearest build-once-reuse-for-Tournament opportunity in this whole review: extend document_uploads with a nullable subject_type (player / staff, later club) and matching subject_id, rather than a parallel table — and rather than Tournament inventing its own entrant-eligibility-documents table later.

08 Operational settings and configuration

Club Manager's entire settings surface is renaming the club — confirmed by reading the form directly. clubs.settings jsonb is {} everywhere and unread by any code. Club Admin (IT) has exactly two capabilities: start a "view as" session, and a permission check that is never actually consumed (see §10).

P1 — settings surface is one field wide

Building IT settings nobody asked for "because the role exists" is exactly the anti-pattern to avoid — no integrations, API keys, or email infrastructure exist yet to administer.

09 Reporting and organization visibility

The entire reporting surface is one tab: attendance %, development counts per team, and one club-wide financial summary. No staff, membership, communications, or org-activity report exists.

Three dashboards, one calculation duplicated

ActionCenter, ClubDashboardStats, and the Reports tab are three separate dashboard-shaped surfaces with fuzzy boundaries. ActionCenter and Reports both compute a per-team attendance percentage independently — nothing shares that math.

P1 — consolidate dashboardsP2 — new report types

10 Audit, history, and accountability

write_audit() is used consistently for guardian relationship/permission changes, tournament acknowledgement and roster actions, player team transfer, and primary-coach designation — a real, append-only, no-UPDATE/DELETE-for-anyone log. This part is genuinely good.

Two confirmed gaps, not inferred

Grepping actions.ts for staff add/remove/team-(re)assignment finds zero write_audit calls. Combined with §4's hard delete, a club's entire staffing history can vanish with no record it happened.

view_audit_log is granted to club_manager and club_it_admin — and nobody who holds it can see an audit entry anywhere. The IT page checks the permission only to decide whether to show its "view as" panel, which is a different feature entirely.

P0 — audit the 4 missing call sitesP0 — build the audit viewP2 — verify financial-action coverage

11 Club Admin / IT capability

Exactly two permissions exist: view-as, and the unconsumed audit permission. The "view as" tool itself is well-built — a genuine inspection session, not a takeover; the actor's own identity stays attached to every audit record.

Absent: account deactivation, MFA (none exists to administer), session management beyond view-as's own bookkeeping, integrations, email infrastructure, domains, API keys, security monitoring beyond raw audit rows, and any escalation to Platform Admin.

P0 — audit view, directory fix P1 — account deactivation Defer — MFA, integrations, API keys, domains

A foundational collision with the next phase

IT administration is entirely club_id-scoped. An org with the Tournament entitlement and no Club entitlement has no club, and therefore no IT admin capability of any kind is reachable for it. See §13.

12 Organization → Platform Admin support

Nothing exists — no ticket table, no status field, no escalation path, confirmed by exhaustive search. impersonation_sessions is a related but distinct mechanism and should not be stretched into a support ticket.

P1 — missing, not blockingShared platform capability

Scope as support_requests + support_request_messages, generic over org_id from day one, so it needs zero changes when Tournament-only orgs exist. Reuse start_impersonation()'s pattern for "request temporary access" rather than building a second mechanism.

13 Cross-cutting gaps & Tournament collision risk

Per the request's explicit ask: where today's Club-only design will actively fight the Tournament entitlement if left unaddressed.

Highest-priority finding in the review

IT administration is club-scoped and therefore unreachable for a Tournament-only org (§11). is_org_admin() already exists and is club-independent — the likely fix is extending IT authority to key off org-level authority with club scoping as a narrowing, not a requirement. This should be decided deliberately now, not discovered mid-build the way the team-assignment bug was discovered mid-fix in the prior phase.

Second-highest risk

The role/permission model (has_staff_permission, scope ∈ {club, team}) is Club-shaped by construction. Tournament already has its own, separate staffing concept (org_officials, tournament_officials, referees) for the unrewritten Tournament Manager app. The risk isn't that these compete today — it's defining a new Tournament role model from scratch instead of extending permissions.scope with a tournament/entry value and reusing the existing machinery. Answer this first in the Tournament scoping pass, before any Tournament-specific tables are added.

Also flagged: the documents subject_type extension (§7) should land now specifically because Tournament will be its second consumer; club-vs-org branding precedence (§2) needs a rule before a combined-entitlement org has both and they conflict; the staff-notification resolver (§5) should be built generically so Tournament officials inherit it; and role_assignments remains completely empty — Tournament scoping should not be tempted to build against a table nothing actually writes to.

Before the Tournament pass

Three decisions should be made before, not during, Tournament scoping, because they change the shape of everything that follows:

  1. Authorization model reuse — extend has_staff_permission's scope model rather than inventing a parallel one for officials/entries.
  2. IT administration's scoping — org-level authority with club as a narrowing, not a requirement, or Tournament-only orgs have no IT capability by construction.
  3. Documents' subject_type extension — land this as part of Club cleanup specifically because Tournament will be the second consumer.

Everything else can proceed independently — but these three are the parts of the Club entitlement that Tournament will either compose with cleanly or collide with directly, and which is which depends entirely on whether they're generalized now or left Club-shaped.
